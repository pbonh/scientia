# The C4 model for visualising software architecture

> Source: https://c4model.com/ (plus the linked `/abstractions` and
> `/diagrams` pages). Retrieved 2026-05-26 via web fetch. Licensed
> CC BY 4.0 International. Written by its creator, Simon Brown.

The C4 model is an easy to learn, developer friendly approach to software
architecture diagramming. It is the official approach for "visualising
software architecture", and the site is maintained by its creator, **Simon
Brown**.

The C4 model is made up of:

1. A hierarchical set of **abstractions** — software systems, containers,
   components, and code.
2. A hierarchical set of **diagrams** — system context, container,
   component, and code.
3. A set of **supplementary diagrams** — system landscape, dynamic, and
   deployment.
4. **Notation independent** — not tied to any particular notation (e.g.
   UML, ArchiMate, etc.).
5. **Tooling independent** — usable with any tool, from whiteboards and
   sticky notes to diagramming software.

It is an **"abstraction-first" approach** to diagramming software
architecture, based upon abstractions that reflect how software architects
and developers think about and build software. The metaphor is that the
diagrams are **maps of your code** at various levels of detail — much like
zooming in and out of an online map (e.g. the whole world, then a country,
then a region, then a street).

## A common set of abstractions

The C4 model considers the static structures of a software system in terms
of the following abstractions:

- **Person** — people (actors, roles, personas, named individuals, etc.)
  use the software systems that we build.
- **Software System** — the highest level of abstraction; describes
  something that delivers value to its users, whether they are human or
  not. A software system is made up of one or more containers.
- **Container** — an application or a data store. A container is something
  that needs to be running in order for the overall software system to
  work (e.g. a server-side web application, single-page application,
  desktop application, mobile app, database schema, file system, etc.). A
  container is *not* a Docker container — it is a separately deployable /
  runnable unit that executes code or stores data. Each container contains
  one or more components.
- **Component** — a grouping of related functionality encapsulated behind a
  well-defined interface. A component is *not* separately deployable; it
  runs inside a container. Each component is implemented by one or more
  code elements.
- **Code element** — for example, classes, interfaces, objects, functions,
  database tables, etc.

Summarised: "A software system is made up of one or more containers
(applications and data stores), each of which contains one or more
components, which in turn are implemented by one or more code elements
(classes, interfaces, objects, functions, etc)."

## A common set of diagram types

The C4 model is named after the core set of hierarchical **static
structure** diagrams:

1. **System Context diagram** — the starting point; shows the software
   system in scope as a box in the centre, surrounded by its users and the
   other systems it interacts with. The focus is on people (actors, roles,
   personas) and software systems rather than technologies, protocols, and
   other low-level detail. It is the "big picture" — good for non-technical
   and technical audiences alike.
2. **Container diagram** — zooms into the software system, showing the
   high-level technical building blocks (containers) and how they
   interact, including the major technology choices and how responsibilities
   are distributed across them. Audience: technical people inside and
   outside the team.
3. **Component diagram** — zooms into an individual container to show the
   components inside it, their responsibilities, and the technology/
   implementation details. Audience: software architects and developers.
4. **Code diagram** — (optional, rarely needed) zooms into an individual
   component to show how it is implemented, typically using a UML class
   diagram or entity relationship diagram. Often best auto-generated by
   tooling (IDE, modelling tool) rather than drawn by hand.

You don't need to use all four levels of diagram — only those that add
value. The **system context and container diagrams are sufficient for most
software development teams.**

### Supplementary diagrams

Three supplementary diagram types complement the core hierarchy:

- **System Landscape diagram** — a way to show the bigger picture of the
  enterprise / IT landscape: all of the software systems, the people who
  use them, and how they are related, regardless of whether they are in
  scope for the team. It is essentially a system context diagram without a
  specific system in focus.
- **Dynamic diagram** — shows how elements collaborate at runtime to
  implement a feature, user story, use case, workflow, etc. Numbered
  interactions describe the order of the collaboration (similar to a UML
  sequence/collaboration diagram, but simplified).
- **Deployment diagram** — shows how instances of software systems and/or
  containers are mapped to the infrastructure (deployment nodes such as
  physical servers, virtual servers, containers, executors, cloud
  services, etc.) on which they run.

## Notation

The C4 model doesn't prescribe a particular notation. A simple notation
that works well on whiteboards, sticky notes, and diagramming tools is
recommended: each element should include a name, the element type (Person,
Software System, Container, Component), the technology where appropriate,
and a short description of responsibilities. Lines represent relationships,
and should be unidirectional with a label describing the intent/purpose and
optionally the technology/protocol. Diagrams should have a title, and a key
/ legend explaining the notation used.

## Tooling and resources

The site links to an interactive example, an O'Reilly-published book, video
content, training and workshops, and a community (Patreon and Discord). The
C4 model itself is notation- and tooling-independent and can be used with
anything from a whiteboard to dedicated diagramming-as-code tools.
